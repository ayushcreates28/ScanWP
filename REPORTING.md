# Reporting

Reports are generated from canonical structured database observations. Each site and the consolidated portfolio receive JSON, HTML, Excel and PDF. Reports include execution/coverage, core/PHP and component inventory, pending updates, advisory identifiers/ranges/corrected branches, publisher severity/CVSS, internal priority/confidence, source links/notices, configuration/exposure/integrity observations, historical changes and limitations. The installed inventory is complete only for what authenticated WordPress APIs enumerate for that site; must-use loaders and vendor metadata can require manual review.

`complete` describes executed scope and usable required data, not a clean website. `partial`, `failed`, `skipped`, `cancelled` and `interrupted` are never translated into a secure result. “Verified findings” counts current open observations with confirmed evidence; it includes configuration/update findings as well as confirmed affected versions. Potential advisory matches stay distinct. Missing CVSS stays unknown. Basic header presence does not prove an effective policy. XML-RPC, REST and public author metadata availability alone are informational.

Version matching supports numeric/prerelease/patch versions and multiple inclusive/exclusive ranges. Unparseable PHP/WordPress version forms remain unknown instead of being string-compared. Core/update-API identities can be confirmed; custom directory hints, premium, theme and must-use identities require verification. A confirmed affected version does not prove exploitability, exploitation or malware. Internal priority can be raised by critical business context without changing publisher data. Authentication/exploitation context not supplied by the implemented source schema remains unknown; no hosting-level CVE matching is claimed.

History changes: new, recurring, resolved, verification required, not comparable. Resolution requires an explicit comparable clear observation. Missing inventory, missing advisory, stale feed, disappeared component or blocked check cannot clear a prior finding. Outstanding unverified observations are carried forward. A changed file is not automatically malicious; “known-clean” means a match against the operator-supplied trusted manifest only.

XLSX tabs: Summary, Sites, Findings, Inventory, Checks, History. Values are static canonical exports, without formulas or external links. Potential formula prefixes are escaped as text. Source notices and references are retained with their findings. Long cell text remains available in the cell editor; use HTML/PDF/JSON for very long narratives. Excel's cell-size limit causes an explicit export failure, never silent text truncation.

HTML escapes all remote text and has a restrictive offline CSP. PDF uses paginated text rather than oversized unsplittable tables, with escaped markup and no fetched resources. Non-ASCII PDF text is represented with Unicode escapes to avoid silently missing glyphs in the portable base font; HTML/Excel retain Unicode. Some Python schema keys remain in technical details; unknown values are explicit. Report files use restrictive Unix modes; Windows requires private folder ACLs.

Optional Codex integration uses the Responses API with no tools and an enumerated output schema. It receives only aliased finding IDs, enumerated priorities and confidence. Remote titles, HTML, logs, descriptions, versions and secrets are excluded. The adapter validates returned IDs and rejects extra claims. It can reorder recorded actions; facts and management prose remain deterministic. AI failure falls back to the deterministic summary. A real Codex call/model has not been verified; the operator must select a supported model. [Structured Outputs documentation](https://developers.openai.com/api/docs/guides/structured-outputs).

`audit-engine/examples/reports` contains clearly labeled **TEST DATA ONLY** artifacts. They do not report findings about Quadigy or any client website. Do not publish real client reports or histories in source control.
